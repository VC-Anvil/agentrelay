# Importación atómica de planes — AgentRelay v0.4

`Store.action("create_plan", data, actor="human")` acepta exactamente `{request_id, tickets}`. `request_id` tiene 1–128 caracteres sin espacios exteriores; `tickets` contiene 1–64 objetos, cada uno con `key` único de 1–64 caracteres sin espacios exteriores, campos de `create_ticket`, `parent_key`, `depends_on_keys` y `status` opcional (`backlog` o `queued`). El estado por defecto es `backlog`; el de `create_ticket` sigue siendo `queued`. `parent_key` y `parent_id` son excluyentes. `depends_on` puede combinar IDs existentes con `depends_on_keys` locales; se rechazan duplicados tras resolverlos. Las claves locales pueden referirse a entradas posteriores. Los IDs externos deben existir antes del plan.

El resultado es `{request_id, key_to_id, tickets}`. Se inserta todo en una transacción SQLite `BEGIN IMMEDIATE`, con eventos `create_plan_ticket` por ticket y un evento `create_plan` con el mapa. La comprobación del grafo incluye jerarquía y dependencias. Cualquier error revierte tickets, secuencia de IDs, eventos y registro de idempotencia. La tabla nueva `plan_requests` se crea con `IF NOT EXISTS` al abrir bases existentes. La misma combinación de `request_id`, actor y carga JSON canónica devuelve el resultado original sin nuevos eventos; reutilizar el ID con otro actor o carga da 409. No se cambia ningún ticket existente ni se ejecuta trabajo.

`tests/test_plan_import.py` cubre referencias adelantadas, padre y dependencia externos, estados y perfil, auditoría, rollback ante ciclo detectado al final, ciclos mixtos, relaciones ambiguas, límites, perfiles inválidos e idempotencia concurrente y tras reabrir la base. Tras la revisión de integración añadí regresiones para IDs externos con espacios, `parent_id` vacío, claves locales con espacios y Unicode inválido. Los IDs externos se normalizan antes de persistirse; los identificadores locales con espacios exteriores se rechazan.
