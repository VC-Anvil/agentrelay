# Atomic caller-scoped claim service

`Store.action("claim_next_ticket", data, actor)` accepts exactly `request_id`, `candidates`, `assignee`, `actual_model` and `actual_effort`. Each of 1–64 candidates contains exactly `ticket_id` and `expected_revision`. Identifiers use the existing `create_plan` rule: 1–128 characters, with no leading or trailing whitespace; internal spaces are permitted. Revisions are positive integers, excluding booleans. A nonhuman actor must match the assignee identity.

One `BEGIN IMMEDIATE` transaction validates every candidate ID, classifies ineligible candidates and claims at most one eligible ticket. An unknown ID aborts the whole call with 404. Skips preserve candidate order and use `stale_revision`, `not_ready`, `missing_acceptance` or `incompatible_profile`. Astra candidates require declared `gpt-6-astra` and `high` exactly. Eligible candidates are ranked urgent, high, normal, low, then creation time and ID. The service calls the existing `_claim` path for the selected ticket, preserving its ordinary audit event and revision guard; it never searches outside the supplied candidates.

The result is `{request_id, ticket: full_ticket|null, skipped: [{ticket_id,reason}]}`. The new `claim_requests` table stores actor, canonical full-payload hash and historical result, including an idle result. An exact retry returns that same result before consulting current ticket state, without a new event or mutation; a reused ID with another actor or payload returns 409. A separate global `claim_next_ticket` event records request ID, selected ticket ID or null, and skips. SQLite backup includes receipts; bulk export does not add them. A receipt describes the past claim decision, not current ticket status or acceptance.

`create_plan` and `claim_next_ticket` share the request-ID namespace within one database, even though their receipts live in separate tables. An ID already used by the other action returns 409 before any ticket or event change. Each action still returns its own preexisting receipt on an exact replay; this also preserves historical receipts in databases that might already have both tables populated.

`tests/test_claim_next.py` uses temporary databases and independent `Store` instances. It covers two simultaneous distinct requests claiming two reviewed tickets, concurrent replay of one request, priority and tie order, candidate scope, hierarchy/dependencies/status/acceptance/Astra skips, unknown-ID rollback, strict envelope and bounds, canonical key-order replay, changed-state and idle historical receipts, backup recovery, and absence of duplicate audit events. **10/10 tests passed** locally in 17.262 s after the whitespace-contract correction; the added key-order replay assertion passed in a focused rerun (1/1, 1.611 s). `git diff --check` passed. No provider or inference was invoked.

After cross-action ID guards were added, two further tests verify plan→claim and claim→plan both return 409, preserve tickets/events/receipts and leave each original exact replay working. The package's **12/12 tests passed** locally in 18.801 s. This supersedes the earlier 10-test count; no full-suite or CI result is claimed here.

Limits: this operation only claims work the caller already selected and reviewed; it does not verify that review, acceptance quality, actual model execution, or eventual ticket completion. It does not claim SQL or token savings. The root integrator owns HTTP/MCP/CLI exposure and full-suite/CI evidence.
