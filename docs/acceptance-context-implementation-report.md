# CAS del contexto de aceptación — implementación de servicio AR-0049

Se añadió `acceptance_context` a `Store.context`: vale `null` fuera de `review` y, dentro, devuelve `{schema_version:1,token,children_count,dependencies_count,source_checks_count}`. `token` tiene formato `sha256:` seguido de 64 dígitos hexadecimales minúsculos. El contexto y la huella se calculan en la misma transacción de lectura.

La huella alimenta SHA-256 con el dominio `agentrelay.acceptance_context.v1`, registros JSON UTF-8 compactos etiquetados y longitud prefijada: ticket `id/revision/status`; hijos inmediatos `id/revision/status/parent_id` ordenados por ID; dependencias inmediatas `id/revision/status` ordenadas por ID; total de source checks y los últimos tres recibos visibles, con `check_id/snapshot_id/report_sha256/ticket_revision` en el mismo orden de `context`. Se procesan las relaciones fila a fila. El token y sus metadatos tienen tamaño fijo; el trabajo de lectura es lineal en hijos y dependencias. No se recorren nietos ni se incorporan comentarios, cursores, perfil, runs o contenido de archivos externos.

`complete_ticket` exige `expected_acceptance_context_token`. Valida forma exacta antes de leer el ticket (400 si falta o es inválido), conserva CAS de revisión, estado, identidad y criterios, recalcula la huella dentro de `BEGIN IMMEDIATE` y devuelve 409 sin mutación si ya no coincide. Después comprueba bloqueadores y sólo entonces pasa a `done`. El evento de éxito añade `acceptance_context_schema_version:1` y `expected_acceptance_context_token`. No hay migración ni aceptación automática. Los clientes que llamaban a `complete_ticket` sin el nuevo campo recibirán 400 hasta adoptar la lectura previa de `Store.context`; la raíz actualiza CLI/MCP/UI y los fixtures antiguos.

`tests/test_acceptance_context.py` prepara catorce pruebas para la reproducción del hijo añadido y terminado, cambios de pertenencia, reapertura y nueva aceptación de hijos/dependencias, comentarios y paginación, cambios directos de revisión, inserción/replay/cuarto source check, exclusión de nietos, tokens inválidos y rollback, backup, concurrencia de dos revisores y 120 hijos inmediatos. Una regresión adicional muestra que crear un hijo, cancelarlo y desprenderlo durante `review` restaura el material inmediato original y, con él, el mismo token: la huella no certifica una historia de eventos monótona. Los tests usan acciones públicas para ciclos y relaciones; el fixture de source checks usa un snapshot local explícito, sin proveedor ni inferencia.

Esa evidencia funcional corresponde al host, no a este especialista; la suite completa y la UI quedan bajo integración de la raíz. La huella compara estado gestionado por Store; no firma datos ni acredita que el revisor haya leído o entendido el contexto.
